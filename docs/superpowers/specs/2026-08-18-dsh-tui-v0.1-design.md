# dsh-tui v0.1 Design

## Objective

Ship a real, installable DeepSeek Harness terminal client that is reliable enough for public GitHub use and visually clear enough for a short Douyin demonstration. The first release optimizes for a convincing end-to-end experience: start the app, send a Chinese coding task, watch tool activity, make a safe approval decision, interrupt work, start a fresh session, and see the final result.

The plan is organized by deliverables, not weeks or time estimates. Implementation should continue autonomously across related work. Automated checks are part of each batch, not manual user-review gates.

## Product Scope

v0.1 includes:

- One-command CLI startup from an npm package.
- A real DeepSeek Harness ACP backend, with Echo mode retained only for tests and offline demonstration.
- Markdown conversation rendering, compact tool cards, approval overlays, token/cost status, interruption, real fresh-session creation, and read-only history replay.
- Windows, macOS, and Linux-compatible configuration and process launching.
- Automated unit, integration, PTY, packaging, and CI checks.
- GitHub release assets and a reproducible Douyin demo flow.

v0.1 deliberately excludes:

- Continuing an old durable session. The DSH rc.7 ACP contract supports fresh sessions only.
- A settings marketplace, theme marketplace, full terminal emulator, remote synchronization, and a second plugin system.
- Blind backend-crash retries or automatic replay of prompts that may have caused side effects.

## Architecture

Keep the current `@earendil-works/pi-tui` rendering layer and ACP approach so the release does not become a wholesale rewrite. Replace the current monolithic wiring and brittle side effects with narrow modules:

```text
bin/dsh-tui.js
  -> src/main.ts
       -> src/cli.ts
            -> src/config.ts
            -> src/app.ts
                 -> src/backend/acp-client.ts
                 -> src/backend/session-log.ts
                 -> src/controller.ts
                 -> src/ui/*
                 -> src/policy.ts
                 -> src/usage.ts
                 -> src/text.ts
       -> src/text.ts (fatal-boundary sanitization only)
```

Responsibilities:

- `src/main.ts`: minimal process entry; call `runCli()`, catch only top-level failures, and set `process.exitCode` after cleanup.
- `src/cli.ts`: own help/version parsing and decide whether to print, run Echo mode, or launch the interactive app.
- `src/app.ts`: composition root for terminal, ACP client, log reader, controller, and view; install and remove process cleanup handlers exactly once.
- `src/config.ts`: parse CLI/environment values into one validated `AppConfig`; resolve paths without shell-string splitting.
- `src/backend/acp-client.ts`: own JSON-RPC framing, child-process lifecycle, fresh sessions, one in-flight prompt, permission replies, cancellation notifications, and awaited shutdown.
- `src/backend/session-log.ts`: own DSH JSONL path resolution, incremental tailing, partial-line buffering, call/result correlation, usage events, and read-only history parsing.
- `src/controller.ts`: own application state transitions. UI components render state and emit intents; they do not independently decide lifecycle or permission policy.
- `src/ui/*`: own transcript, status, editor, approval overlay, and history overlay. Every overlay owns input focus and returns a typed result.
- `src/policy.ts`: pure, fail-closed command/tool classification.
- `src/usage.ts`: pure disjoint-token aggregation and pricing.
- `src/text.ts`: strip unsafe terminal controls and produce terminal-width-safe one-line summaries.

The custom ACP composition uses raw JSONL (`persistenceCompression: none`) because v0.1 intentionally consumes the log as an observability side channel. The limitation is explicit and contract-tested. ACP remains the source for prompts, committed answers, cancellation, and permission requests; the log remains the source for tool activity and usage.

## Session Semantics

- `newSession()` creates a new ACP session and resets transcript, usage, cost, watcher state, and visible session identity.
- History selection is read-only transcript replay. It never changes the active ACP session and never claims that the next prompt continues the selected history.
- The UI uses the label “History”, not “Resume”.
- A backend crash marks the current operation as having an unknown outcome. The user may submit again manually after inspecting state; the client never resubmits automatically.

## Safety and Failure Handling

- Permission handling fails closed. Missing handlers, empty options, invalid choices, overlay cancellation, and shutdown all resolve to rejection/cancellation.
- A shell command is routine only when the complete parsed command is provably read-only. Chaining, pipes, redirects, command substitution, or publish/delete/push operations cannot inherit a benign prefix classification.
- Model text, tool arguments, paths, errors, and log-derived content are stripped of terminal control sequences before rendering.
- Only one prompt may be in flight. Additional submissions receive a visible “already working” message and are not sent.
- `session/cancel` is emitted as a JSON-RPC notification. The prompt request settles independently with its ACP stop reason.
- Shutdown waits for backend disposal, then escalates from stdin close to termination and forced kill only when necessary.
- Uncaught failures restore the terminal and exit non-zero; the app does not continue in an unknown state under a “never crash” promise.

## Configuration and Distribution

- Published package: `@nico0713520/dsh-tui` unless the npm account uses a different confirmed scope.
- Installed executable: `dsh-tui`.
- Supported Node versions: `^22.19.0 || >=24.0.0`, matching DSH rc.7.
- DSH packages are pinned to one tested release-candidate version. The application launches the published `dsh-acp-demo` executable and ships its own `cordis.yml`; users do not clone the DSH repository.
- Precedence: CLI options, then environment variables, then platform-safe defaults.
- `DSH_ACP_CMD_JSON` accepts a JSON string array for advanced overrides. A plain shell command string is not split by spaces.
- Session data defaults to a user-data directory; tests and demonstrations can override it with `DSH_PERSIST_ROOT`.

## Testing Strategy

The automated suite is the execution gate. It should run without a DeepSeek API key except for an explicitly separate live test.

- Unit tests: config, command classification, text sanitization, usage/pricing, history parsing, and incremental log decoding.
- ACP integration tests: a deterministic fake JSON-RPC child process covers initialize, prompt, permission, cancel notification, timeout, exit, new session, and shutdown.
- PTY tests: launch the real TUI and exercise editor submission, overlay navigation, Escape precedence, double Ctrl+C, resize, and CJK rendering.
- Package tests: pack the tarball, install it into a temporary directory, run help/version/offline smoke, and verify the file allowlist.
- Live test: one real model turn with a tool call, approval allow/reject, cancellation, and a fresh session. It is opt-in and must fail non-zero when enabled and unsuccessful.

## Autonomous Execution Policy

Implementation is grouped into broad coding batches. Within a batch, the agent may create tests, refactor the listed modules, run checks, repair failures, and commit the completed batch without asking for intermediate approval. Human input is needed only for unavailable credentials, npm/GitHub publication authority, destructive external operations, or a product decision that changes this design.

## Release Deliverables

- Public GitHub repository with MIT license, CI, topics, screenshots, concise English README, Chinese README, and a tagged v0.1 release.
- Installable npm tarball/package whose first README command works in a clean environment.
- A sanitized vertical demo recording showing startup, a Chinese task, tool activity, a high-risk approval decision, and verified completion.
